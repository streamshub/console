= Enabling a metrics provider

[role="_abstract"]
Configure the console deployment to enable a metrics provider. 
You can set up configuration to use one of the following sources to scrape metrics from Kafka clusters using Prometheus:

OpenShift's built-in user workload monitoring::
Use OpenShift's workload monitoring, incorporating the Prometheus operator, to monitor console services and workloads without the need for an additional monitoring solution.
A standalone Prometheus instance::
Provide the details and credentials to connect with your own Prometheus instance.
An embedded Prometheus instance (default):: 
Deploy a private Prometheus instance for use only by the console instance. 
The instance is configured to retrieve metrics from all Strimzi managed Kafka instances in the same Kubernetes cluster. 
Using embedded metrics is intended for development and evaluation only, not production.

Example configuration for OpenShift monitoring and a standalone Prometheus instance is provided in the following files: 

* `examples/console/console-openshift-metrics.yaml`
* `examples/console/console-standalone-prometheus.yaml`

You can define Prometheus sources globally as part of the console configuration using `metricsSources` properties:

`metricsSources`:: Declares one or more metrics providers that the console can use to collect metrics.
`type`:: Specifies the type of metrics source. Valid options:
  - `openshift-monitoring`
  - `standalone` (external Prometheus)
  - `embedded` (console-managed Prometheus)
`url`:: For `standalone` sources, specifies the base URL of the Prometheus instance.
`authentication`:: (For `standalone` and `openshift-monitoring` only) Configures access to the metrics provider using `basic`, `bearer` token, or `oidc` authentication.
`trustStore`:: (Optional, for `standalone` and `openshift-monitoring`) Specifies a truststore for verifying TLS certificates when connecting to the metrics provider.
Supported formats: `JKS`, `PEM`, `PKCS12`.
Content may be provided using a `ConfigMap` or a `Secret`.
A truststore is required when the metrics endpoint presents a TLS certificate signed by a CA that is not already in the console's default trust store.
This is common for `openshift-monitoring`, where the console connects to the Thanos Querier route, which on a default OpenShift cluster presents a self-signed certificate.

Assign the metrics source to a Kafka cluster using the `kafkaClusters.metricsSource` property.
The value of `metricsSource` is the `name` of the entry in the `metricsSources` array.

The `metricsSources` entry for `embedded` requires no properties besides the `type`.
The `openshift-monitoring` entry additionally supports `authentication` and, in most deployments, requires a `trustStore`: the console connects to the OpenShift Thanos Querier route over HTTPS, and when that route uses a self-signed or private CA (the default on OpenShift) the CA must be supplied so the console can validate the connection.
For a complete example, see `examples/console/console-openshift-metrics-self-signed-cluster-ca.yaml`.
However, this configuration only tells the console where to _read_ metrics from.
In all cases, you must separately configure each Kafka cluster to _expose_ Prometheus metrics; the console does not do this for you.

[NOTE]
====
Regardless of the metrics source type, each `Kafka` resource must expose Prometheus metrics through the `spec.kafka.metricsConfig` property, as shown in the example `Kafka` (`console-kafka`) and `ConfigMap` (`console-kafka-metrics`) resources in `examples/kafka`.
The console reads these metrics but does not configure metrics exposure on the Kafka cluster.
For more information, see link:{BookURLConfiguring}#con-common-configuration-prometheus-reference[configuring metrics in the Strimzi documentation^].

The responsibility for scraping the exposed metrics into Prometheus depends on the source type:

* `embedded`: the operator deploys a private Prometheus instance that automatically scrapes the metrics endpoints exposed by your Strimzi-managed Kafka clusters. You must still enable `metricsConfig` on each `Kafka` resource. Using embedded metrics is intended for development and evaluation only, not for production environments.
* `openshift-monitoring`: you must also enable monitoring for user-defined projects in OpenShift and provide a `PodMonitor` to scrape the Kafka pods, as shown in `examples/prometheus/040-PodMonitor-kafka-resources.yaml`. See the https://docs.openshift.com/container-platform/latest/observability/monitoring/enabling-monitoring-for-user-defined-projects.html[OpenShift documentation on enabling monitoring for user-defined projects^].
* `standalone`: your Prometheus instance must be configured to scrape the Kafka pods and be accessible from the console.
====

.Example metrics configuration for Openshift monitoring
[source,yaml]
----
apiVersion: console.streamshub.github.com/v1alpha1
kind: Console
metadata:
  name: my-console
spec:
  hostname: my-console.<cluster_domain>
  # ...
  metricsSources:
    - name: my-ocp-prometheus
      type: openshift-monitoring
      # Required when the Thanos Querier route uses a self-signed CA (the default on
      # OpenShift). On most clusters the cluster root CA (kube-root-ca.crt, available in
      # every namespace) is sufficient. See the note below if this does not resolve the
      # error on your cluster.
      # trustStore:
      #   type: PEM
      #   content:
      #     valueFrom:
      #       configMapKeyRef:
      #         name: kube-root-ca.crt
      #         key: ca.crt
  kafkaClusters:
    - name: console-kafka
      namespace: kafka
      listener: secure
      metricsSource: my-ocp-prometheus
      credentials:
        kafkaUser:
          name: console-kafka-user1
  # ...        
----

[NOTE]
====
If the console logs a `PKIX path building failed` error from `MetricsService`, the metrics client could not validate the TLS certificate presented by the metrics endpoint.
For an `openshift-monitoring` source, the console connects to the `thanos-querier` route, which presents a self-signed certificate on a default OpenShift cluster.

Set `metricsSources[].trustStore` to the cluster root CA using the `kube-root-ca.crt` `ConfigMap`, which is available in every namespace, as shown in `examples/console/console-openshift-metrics-self-signed-cluster-ca.yaml`.
On most clusters this is sufficient, because the route's signing CA is included in the cluster root CA bundle (for example on managed or hosted OpenShift, or when a single custom CA signs the whole cluster).

If the `PKIX` error persists with `kube-root-ca.crt`, the Thanos Querier route is signed by a separate ingress CA that is not in the cluster root CA bundle.
In that case, supply the CA that actually signs the route instead.
To identify it, inspect the certificate the route presents:

[source,shell]
----
HOST=$(oc get route thanos-querier -n openshift-monitoring -o jsonpath='{.spec.host}')
echo | openssl s_client -connect "$HOST:443" 2>/dev/null | openssl x509 -noout -issuer
----
====

.Example metrics configuration for standalone Prometheus monitoring
[source,yaml]
----
apiVersion: console.streamshub.github.com/v1alpha1
kind: Console
metadata:
  name: my-console
spec:
  hostname: my-console.<cluster_domain>
  # ...
  metricsSources:
    - name: my-custom-prometheus
      type: standalone
      url: <prometheus_instance_address>
      authentication:
        basic:
          username: my-user
          password: my-password
      trustStore:
        type: JKS
        content:
          valueFrom:
            configMapKeyRef:
              name: my-prometheus-configmap
              key: ca.jks
        password:
          value: truststore-password
  kafkaClusters:
    - name: console-kafka
      namespace: kafka
      listener: secure
      metricsSource: my-custom-prometheus
      credentials:
        kafkaUser:
          name: console-kafka-user1
  # ...
----

* `metricsSources.name` defines a unique name for the metrics source.
* `metricsSources.type` specifies the type of metrics source. Use `standalone` for an external Prometheus instance.
* `metricsSources.url` specifies the URL of the standalone Prometheus instance used for metrics collection.
* `metricsSources.authentication` defines the authentication configuration used to access the Prometheus instance.
** `basic` specifies basic authentication and requires a `username` and `password`.
** `bearer` specifies bearer token authentication and requires a `token`.
** `oidc` specifies OpenID Connect authentication. For details, see xref:ref-authentication-options-{context}[Using an OIDC provider to secure access to Kafka clusters].
* `metricsSources.trustStore` optionally defines a truststore used to validate the metrics provider TLS certificate. Supported formats include `JKS`, `PEM`, and `PKCS12`. Truststore content can be provided by using either a ConfigMap or a Secret.
* `metricsSources.trustStore.password` optionally specifies the truststore password. The password can be provided as a plaintext value or via a Secret. Plaintext values are not recommended for production environments.
* `kafkaClusters.metricsSource` associates the Kafka cluster with the configured metrics source.
