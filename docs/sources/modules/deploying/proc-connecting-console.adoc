= Deploying and connecting the console to a Kafka cluster

[role="_abstract"]
Use the console operator to deploy the StreamsHub Console to the same Kubernetes cluster as a Kafka cluster managed by Strimzi. 
Use the console to connect to the Kafka cluster.

.Prerequisites

* xref:con-deploying-prereqs-{context}[Deployment prerequisites].
* The console operator is deployed to the Kubernetes cluster.

.Procedure

. Create a `Console` custom resource in the desired namespace. 
+
If you deployed the xref:proc-deploying-kafka-{context}[example Kafka cluster] provided with the installation artifacts, you can use the configuration specified in the `examples/console/010-Console-example.yaml` configuration file unchanged.
+
Otherwise, configure the resource to connect to your Kafka cluster.
+
.Deploying the console with an example configuration for connecting to a Kafka cluster
[source,yaml]
----
apiVersion: console.streamshub.github.com/v1alpha1
kind: Console
metadata:
  name: my-console
spec:
  hostname: my-console.<cluster_domain>
  kafkaClusters:
    - name: console-kafka
      namespace: kafka
      listener: secure
      properties:
        values: []
        valuesFrom: []
      credentials:
        kafkaUser:
          name: console-kafka-user1
----

* `hostname` defines the hostname used to access the console over HTTP.
* `kafkaClusters.name` specifies the name of the Strimzi `Kafka` resource that represents the cluster.
* `kafkaClusters.namespace` specifies the namespace where the `Kafka` resource is deployed.
* `kafkaClusters.listener` specifies the listener used to expose the Kafka cluster for console connections.
* `kafkaClusters.properties.values` optionally defines additional connection properties.
* `kafkaClusters.properties.valuesFrom` optionally specifies ConfigMaps or Secrets that provide connection properties.
* `kafkaClusters.credentials.kafkaUser.name` optionally specifies the Strimzi `KafkaUser` resource used for authenticated access to the Kafka cluster.
The operator reads the credential `Secret` generated by Strimzi for that user.
Before the operator can read it, the per-Console ServiceAccount must be explicitly granted `get` access on that `Secret` in the `KafkaUser` namespace.
+
The Console ServiceAccount name follows the pattern: `<console-name>-console-serviceaccount`, in namespace `<console-namespace>`.
+
Create a `Role` and `RoleBinding` in the namespace where the generated `KafkaUser` Secret lives
(by default `kafkaClusters.namespace`, or `kafkaClusters.credentials.kafkaUser.namespace` if set).
The `resourceNames` entries must use the actual Secret names from `KafkaUser.status.secret`.
They commonly match the `KafkaUser` names, but the operator uses the status value and it must be verified before creating the Role.
If multiple `KafkaUser` Secrets share the same namespace, a single Role can cover all of them.
+
.Using YAML resources (suitable for GitOps workflows)
[source,yaml]
----
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: console-kafkauser-secret-reader
  namespace: <kafka-namespace>
rules:
- apiGroups: [""]
  resources: ["secrets"]
  resourceNames:
  - <generated-secret-name-1>
  - <generated-secret-name-2>   # use one actual Secret name per KafkaUser Secret
  verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: console-kafkauser-secret-reader
  namespace: <kafka-namespace>
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: console-kafkauser-secret-reader
subjects:
- kind: ServiceAccount
  name: <console-name>-console-serviceaccount
  namespace: <console-namespace>
----
+
.Using the CLI
[source,shell]
----
kubectl create role console-kafkauser-secret-reader \
  --namespace=<kafka-namespace> \
  --verb=get --resource=secrets \
  --resource-name=<generated-secret-name-1> \
  --resource-name=<generated-secret-name-2>   # repeat --resource-name for each Secret

kubectl create rolebinding console-kafkauser-secret-reader \
  --namespace=<kafka-namespace> \
  --role=console-kafkauser-secret-reader \
  --serviceaccount=<console-namespace>:<console-name>-console-serviceaccount
----
+
If the grant is missing, the `Console` resource reports a `SecurityError` condition when the operator uses its default `PRESERVE` action.
The condition lists every Secret that needs a grant along with the exact `kubectl` commands to run.
The `Console` remains not ready, but any denied credentials and configuration already present in an existing deployment are preserved unchanged until access is granted.
If the operator is configured with the `REMOVE` action, it reports a `SecurityWarning`, removes denied KafkaUser credentials, and removes denied Kafka cluster connections from the generated configuration, including an existing deployment.
`REMOVE` provides the strongest protection and may become the default in a future release; `PRESERVE` is currently the default to avoid unexpected credential or connection removal during upgrades.
See xref:ref-operator-configuration-{context}[Configuring the console operator] for the global denial-action setting and the security implications of `IGNORE`.
+
`kafkaClusters.credentials.kafkaUser.namespace` optionally overrides the namespace where the `KafkaUser` and its Secret live, for deployments where the Strimzi User Operator watches a namespace different from the `Kafka` namespace.

. Apply the `Console` configuration to install the console.
+
In this example, the console is deployed to the `console-namespace` namespace:
+
[source,shell]
----
kubectl apply -f examples/console/010-Console-example.yaml -n console-namespace

----

. Check the status of the deployment:
+
[source,shell]
----
oc get pods -n console-namespace
----
+
.Output shows the deployment name and readiness
[source,shell]
----
NAME           READY  STATUS  RUNNING
console-kafka  1/1    1       1
----

. Access the console.
+
When the console is running, use the hostname specified in the `Console` resource (`spec.hostname`) to access the user interface.
