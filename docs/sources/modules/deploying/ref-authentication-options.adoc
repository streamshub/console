= Securing access to the console and Kafka clusters

[role="_abstract"]
Enable secure console access and connections to Kafka clusters using an external OIDC provider or by configuring upstream identity providers via the built-in identity broker (Dex).
Configure the console deployment to connect to an external Identity Provider (IdP) that supports OpenID Connect (OIDC), or configure built-in identity providers for OpenShift OAuth or LDAP.
Also define the subjects and roles for user authorization.
To use group-based authorization as shown in the examples, configure an OIDC provider or identity provider that includes a group membership claim, such as `groups`, in the generated access tokens.
The security profiles can be configured for all Kafka cluster connections on a global level, though you can add roles and rules for specific Kafka clusters.

Example configurations are provided in:
* `examples/console/console-security-oidc.yaml` for external OIDC providers.
* `examples/console/authentication/openshift/console.yaml` for OpenShift OAuth integration.
* `examples/console/authentication/ldap/console.yaml` for LDAP integration.

The configuration introduces the following additional properties for console deployment:

`security`:: Properties that define connection details for external OIDC providers or configured identity providers.
`subjects`:: Specifies the subjects (users or groups) and their roles in terms of JWT claims or explicit subject names, determining access permissions.
`roles`:: Defines the roles and associated access rules for users, specifying which resources (like Kafka clusters) they can interact with and what operations they are permitted to perform.

.Example security configuration for all clusters
[source,yaml]
----
apiVersion: console.streamshub.github.com/v1alpha1
kind: Console
metadata:
  name: my-console
spec:
  hostname: my-console.<cluster_domain>
  security:
    oidc:
      authServerUrl: <OIDC_discovery_URL>
      clientId: <client_id>
      clientSecret:
        valueFrom:
          secretKeyRef:
            name: my-oidc-secret
            key: client-secret
      trustStore:
        type: JKS
        content:
          valueFrom:
            configMapKeyRef:
              name: my-oidc-configmap
              key: ca.jks
        password:
          value: truststore-password
    subjects:
      - claim: groups
        include:
          - <team_name_1>
          - <team_name_2>
        roleNames:
          - developers
      - claim: groups
        include:
          - <team_name_3>
        roleNames:
          - administrators
      - include:
          - <user_1>
          - <user_2>
        roleNames:
          - administrators
    roles:
      - name: developers
        rules:
          - resources:
              - kafkas
            resourceNames:
              - dev-cluster-a
              - com.example.team.*
              - /qa-cluster-[xy]/
            privileges:
              - 'ALL'
      - name: administrators
        rules:
          - resources:
              - kafkas
            privileges:
              - 'ALL'
  kafkaClusters:
    - name: console-kafka
      namespace: kafka
      listener: secure
      credentials:
        kafkaUser:
          name: console-kafka-user1
----

* `security.oidc.authServerUrl` specifies the OIDC provider issuer URI used for endpoint discovery.
* `security.oidc.clientId` specifies the client ID that identifies the console to the OIDC provider.
* `security.oidc.clientSecret` specifies the client secret used to authenticate the console with the OIDC provider.
* `security.oidc.clientSecret.valueFrom.secretKeyRef.name` specifies the name of the Kubernetes `Secret` that stores the client secret.
* `security.oidc.clientSecret.valueFrom.secretKeyRef.key` specifies the key in the `Secret` that contains the client secret value.
* `security.oidc.trustStore` optionally defines a truststore used to validate the OIDC provider TLS certificate. Supported formats include `JKS`, `PEM`, and `PKCS12`. Truststore content can be provided by using either a ConfigMap or a Secret.
* `security.oidc.trustStore.password` optionally specifies the truststore password. The password can be provided as a plaintext value or by reference to a Secret. Plaintext values are not recommended for production environments.

* `security.subjects` defines how users or groups are mapped to roles.
** `security.subjects.claim` specifies the JWT claim used to identify users or groups.
** `security.subjects.include` specifies the users or groups included under the configured claim.
** `security.subjects.roleNames` specifies the roles assigned to the identified users or groups.
** When no `claim` is specified, `security.subjects.include` specifies individual users by name.

* `security.roles` defines the roles available for authorization.
** `security.roles.rules.resources` specifies the resource types that the role can access.
** `security.roles.rules.resourceNames` specifies which resources the role can access.
*** Exact names can be specified, for example `dev-cluster-a`.
*** Wildcard patterns can be specified, for example `com.example.team.*`.
*** Regular expressions can be specified by enclosing the value in slashes, for example `/qa-cluster-[xy]/`.
** `security.roles.rules.privileges` specifies the privileges granted to the role for the selected resources.

If you want to specify roles and rules for individual Kafka clusters, add the details under `kafka.clusters[].security.roles[]`.
In the following example, the `console-kafka` cluster allows developers to list and view selected Kafka resources.
Administrators can also update certain resources.

.Example security configuration for an individual cluster
[source,yaml]
----
apiVersion: console.streamshub.github.com/v1alpha1
kind: Console
metadata:
  name: my-console
spec:
  hostname: my-console.<cluster_domain>
  # ...
  kafkaClusters:
    - name: console-kafka
      namespace: kafka
      listener: secure
      credentials:
        kafkaUser:
          name: console-kafka-user1
      security:
        roles:
          - name: developers
            rules:
              - resources:
                  - topics
                  - topics/metrics
                  - topics/records
                  - groups
                  - nodes/metrics
                  - rebalances
                privileges:
                  - GET
                  - LIST
          - name: administrators
            rules:
              - resources:
                  - topics
                  - topics/metrics
                  - topics/records
                  - groups
                  - groups/configs
                  - rebalances
                  - nodes
                  - nodes/configs
                  - nodes/metrics
                privileges:
                  - GET
                  - LIST
              - resources:
                  - groups
                  - rebalances
                privileges:
                  - UPDATE
----

NOTE: Use `groups` instead of the deprecated `consumerGroups` resource name.
`consumerGroups` is still supported for existing configurations but will be removed in a future release.

== Optional OIDC authentication properties

The following properties can be used to further configure `oidc` authentication.
These apply to any part of the console configuration that supports `authentication.oidc`, such as schema registries or metrics providers.

grantType::
Specifies the OIDC grant type to use. Required when using non-interactive authentication flows, where no user login is involved.
Supported values:
+
* `CLIENT`: Requires a client ID and secret.
* `PASSWORD`: Requires a client ID and secret, plus user credentials (`username` and `password`) provided through `grantOptions`.

grantOptions::
Additional parameters specific to the selected grant type.
Use `grantOptions` to provide properties such as `username` and `password` when using the `PASSWORD` grant type.
+
[source,yaml]
----
oidc:
  grantOptions:
    username: my-user
    password: <my_password>
----

method::
Method for passing the client ID and secret to the OIDC provider.
Supported values:
+
* `BASIC`: (default) Uses HTTP Basic authentication.
* `POST`: Sends credentials as form parameters.

scopes::
Optional list of access token scopes to request from the OIDC provider.
Defaults are usually defined by the OIDC client configuration.
Specify this property if access to the target service requires additional or alternative scopes not granted by default.
+
[source,yaml]
----
oidc:
  scopes:
    - openid
    - registry:read
    - registry:write
----

absoluteExpiresIn::
Optional boolean. If set to `true`, the `expires_in` token property is treated as an absolute timestamp instead of a duration.

== Configuring identity sources using the built-in identity broker

When you configure an identity source using `spec.security.openshift` or `spec.security.ldap`, the operator automatically deploys and manages an embedded Dex instance acting as an identity broker.
Dex authenticates users against OpenShift OAuth or an LDAP directory and issues standard OIDC tokens to the console.

The `oidc`, `openshift`, and `ldap` fields under `spec.security` are mutually exclusive.

=== OpenShift OAuth authentication

You can integrate console authentication with OpenShift's native OAuth server using `spec.security.openshift`.

When `spec.security.openshift` is configured:

* The operator deploys a Dex instance configured with the OpenShift connector.
* Dex uses a dedicated `ServiceAccount` and projected token credentials to communicate with OpenShift OAuth.
* OpenShift users and groups are passed through to the console as OIDC claims.
* Internal communication between the router, Dex, and the console pod is secured using `reencrypt` TLS with certificates issued by OpenShift's service CA.

==== Prerequisites
* OpenShift 4.19 or later (or clusters with the `RouteExternalCertificate` feature gate enabled).

==== Example Console configuration with OpenShift OAuth
[source,yaml]
----
apiVersion: console.streamshub.github.com/v1alpha1
kind: Console
metadata:
  name: my-console
spec:
  hostname: my-console.<cluster_domain>
  security:
    openshift:
      groups:
        - developers
        - cluster-admins
    subjects:
      - claim: groups
        include:
          - cluster-admins
        roleNames:
          - administrators
      - claim: groups
        include:
          - developers
        roleNames:
          - developers
    roles:
      - name: administrators
        rules:
          - resources:
              - kafkas
            privileges:
              - 'ALL'
      - name: developers
        rules:
          - resources:
              - kafkas
            privileges:
              - GET
              - LIST
----

* `security.openshift.groups` optionally restricts logins to members of the listed OpenShift groups. If omitted or empty, all authenticated OpenShift users are allowed to log in.
* `security.openshift.insecureCA` optionally disables TLS certificate verification when communicating with the OpenShift API server (default is `false`).
* `security.openshift.trustStore` optionally defines a custom trust store containing CA certificates if the OpenShift API server uses certificates signed by an untrusted CA.

=== LDAP authentication

You can integrate console authentication with an LDAP directory using `spec.security.ldap`.

When `spec.security.ldap` is configured:

* The operator deploys a Dex instance configured with the LDAP connector.
* Dex searches for users and group memberships based on the configured LDAP queries.
* On plain Kubernetes, TLS is terminated at the Ingress controller and traffic behind the Ingress uses plain HTTP.
* On OpenShift, TLS is re-encrypted using OpenShift service CA certificates.

==== Example Console configuration with LDAP
[source,yaml]
----
apiVersion: console.streamshub.github.com/v1alpha1
kind: Console
metadata:
  name: my-console
spec:
  hostname: my-console.<cluster_domain>
  security:
    ldap:
      host: ldap.example.com:636
      bindDN: uid=serviceaccount,ou=users,dc=example,dc=com
      bindSecret:
        valueFrom:
          secretKeyRef:
            name: ldap-bind-secret
            key: password
      userSearch:
        baseDN: ou=users,dc=example,dc=com
        filter: "(objectClass=person)"
        username: mail
        idAttr: uid
        emailAttr: mail
        nameAttr: cn
        preferredUsernameAttr: uid
      groupSearch:
        baseDN: ou=groups,dc=example,dc=com
        filter: "(objectClass=groupOfNames)"
        userMatchers:
          - userAttr: DN
            groupAttr: member
        nameAttr: cn
    subjects:
      - claim: groups
        include:
          - kafka-admins
        roleNames:
          - administrators
    roles:
      - name: administrators
        rules:
          - resources:
              - kafkas
            privileges:
              - 'ALL'
----

* `security.ldap.host` (required) specifies the host and port of the LDAP server (e.g. `ldap.example.com:636` for LDAPS or `ldap.example.com:389` for plain/StartTLS).
* `security.ldap.bindDN` specifies the DN used to bind to the directory for user and group searches.
* `security.ldap.bindSecret` specifies the password for `bindDN` as a direct `value` or via `valueFrom.secretKeyRef`.
* `security.ldap.insecureNoSSL` specifies whether to connect without TLS encryption (default `false`). Mutually exclusive with `startTLS` and `trustStore`.
* `security.ldap.insecureSkipVerify` specifies whether to skip TLS certificate verification (default `false`). Mutually exclusive with `trustStore`.
* `security.ldap.startTLS` specifies whether to initiate a StartTLS upgrade on a plain connection instead of using LDAPS (default `false`). Mutually exclusive with `insecureNoSSL`.
* `security.ldap.trustStore` optionally defines a custom trust store to validate the LDAP server certificate.
* `security.ldap.userSearch` defines how users are located during authentication:
** `baseDN`: Base distinguished name for user searches.
** `filter`: Search filter combined with the username attribute query.
** `username`: Attribute users enter at the login prompt (for example, `mail` or `uid`).
** `idAttr`: Attribute used as the unique user identifier.
** `emailAttr`: (Required) Attribute mapped to the user email.
** `nameAttr`: Optional attribute mapped to the user's display name.
** `preferredUsernameAttr`: Optional attribute mapped to the user's preferred username.
* `security.ldap.groupSearch` defines how group memberships are resolved:
** `baseDN`: Base distinguished name for group searches.
** `filter`: Search filter combined with the user matching query.
** `userMatchers`: Matches user attributes to group attributes (for example, `userAttr: DN` with `groupAttr: member`).
** `nameAttr`: Attribute containing the group name, which maps to values in `security.subjects`.
